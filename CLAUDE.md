# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A Firefox extension (`extension/`) paired with a Windows-only Python native-messaging host (`host/src/ytmp3_host/`) that downloads YouTube audio as MP3 via `yt-dlp.exe` + `ffmpeg.exe`. The two halves are deployed separately (extension via AMO, backend via an Inno Setup installer) and communicate only through Firefox native messaging over stdio.

## Project priorities

1. **Speed with the best quality.** Downloads must be as fast as possible without lowering audio or cover quality: MP3 is always LAME V0 (`--audio-quality 0`, which encodes as fast as the default V5; 320k CBR is ~2x slower to encode), cover art is a high-quality JPEG (`-q:v 2`). Measure before and after any change to the download pipeline, and never trade quality for speed silently.
2. **Easy to use, install and update.** The main scope of v2 is auto-repair and auto-update logic (e.g. keeping `yt-dlp.exe` current, detecting and fixing a broken host install), so users never have to reinstall manually.
3. **Keep edits small; no refactoring without approval.** When asked to update something, change only the code the task needs: keep each update small and focused, and don't refactor half the app on every edit or create big diffs. If you think a refactor is needed, tell the reviewer and wait for approval before doing it. The goal is to keep the codebase maintainable and avoid unnecessary complexity.
4. **Keep the codebase maintainable.** Avoid unnecessary complexity and keep the codebase clean and organized. Use clear and descriptive names for variables, functions, and classes. Write comments where necessary to explain complex logic or decisions, but do not over do it with them. Rather write longer doc string and use less comments in the code. Follow the existing coding style and conventions used in the project and use state of the art 2026 (we want the modern coding and Python conventions and design patterns).
5. **Tests have to actually test the code.** Do not write tests just so that they happy pass. Make sure the tests actually test the code, real functionality and edge cases. The goal is to have good test coverage that we can rely on and that can catch errors before they reach production. If a test fails, firstly make sure the test is correct and if it is, fix the code. Never adjust a test to make it pass without fixing the code.

## Running tests

The full suites take a while, so don't run them after every edit. While working, run only the tests relevant to the change (e.g. `uv run pytest tests/host/test_core_helpers.py -k folder`, or one `node --test` file). Once those pass, run the full suites once at the end. If that run passes, it is done: don't rerun it to "make sure".

## Layout

- `extension/` — the Firefox add-on (zip this folder for AMO).
- `host/src/ytmp3_host/` — the native host package; `host/tests/` — manual smoke test; `host/bin/` — dev-only `ffmpeg.exe`/`yt-dlp.exe` (gitignored).
- `packaging/installer/` — Inno Setup script; `packaging/assets/` — icons; `packaging/app_manifest.dev.json` — dev native-host manifest template.
- `legacy/v0/`, `legacy/mp4/`, `legacy/popup/` (old toolbar popup) — superseded/experimental code kept for reference. Not packaged; `legacy/v0` still imports the old `mp3` package name, so it does not run as-is.

## Commands

Dependencies are managed with **uv** (Python >= 3.15, see `pyproject.toml`; PyInstaller is in the `dev` dependency group).

```
uv sync                                   # install deps into .venv
uv run python -m ytmp3_host.MP3           # run the native host (blocks reading length-prefixed JSON on stdin)
uv run python host/tests/smoke_native.py  # manual native-messaging smoke test
```

Package the native host from the repo root (output `dist/mp3/mp3.exe` plus `dist/mp3/_internal/`; the command is also recorded at the bottom of `MP3.py`). Keep `--name mp3`: installed v1 manifests point at `mp3.exe`. Use `--onedir`, not `--onefile`: onefile unpacks itself to a temp folder on every launch, and every request starts a new host process. Keep `--exclude-module PIL`: customtkinter tries to import Pillow (for `CTkImage`, unused), so PyInstaller would otherwise bundle the dev-only Pillow from the venv (11 MB). When frozen, `ffmpeg.exe`/`yt-dlp.exe`/`mp3.ico` must sit next to `mp3.exe` (copy them into `dist/mp3/` to run the build directly).

```
uv run pyinstaller --onedir --noconfirm --name mp3 --exclude-module PIL --icon "packaging\assets\mp3.ico" host\src\ytmp3_host\MP3.py
```

Build the installer by compiling `packaging/installer/mp3_installer.iss` with Inno Setup 6. Sources resolve via `{#RepoRoot}` relative to the script: `dist\mp3\*` (recursive), `host\bin\ffmpeg.exe`, `packaging\assets\mp3.ico`. Output: `packaging/installer/output/YT-MP3-Downloader-Setup.exe`.

Release checklist (installed v2 hosts update themselves from the latest GitHub release, see `updater.py`):
1. Bump the version (`__version__`, `pyproject.toml`, `MyAppVersion`; `test_versions.py` checks they match).
2. Build with PyInstaller (optionally check the build: copy `ffmpeg.exe` into `dist\mp3\` and run `dist\mp3\mp3.exe --self-check`, exit code 0), then compile the installer.
3. `uv run python packaging/write_checksums.py packaging/installer/output/YT-MP3-Downloader-Setup.exe` writes `SHA256SUMS` next to it.
4. Publish a GitHub release tagged `vX.Y.Z` (not the 1.x style `v-1.1`, which the updater does not read as a version) with both files under exactly these names. The updater never installs a release without `SHA256SUMS`, and the extension's "Download the installer" link (`INSTALLER_URL`) is `releases/latest/download/YT-MP3-Downloader-Setup.exe`, so the latest release must always carry it: create the release as a draft, upload both files, then publish (a published release without them fails every update until they are there). Publish the host release before an extension version that needs it goes to AMO. A release marked pre-release is never "latest", so it can be staged and tested without reaching users.

Extension tests use Node's built-in runner (no npm dependencies). `tests/extension/harness.js` loads the extension scripts into a `node:vm` sandbox with a fake `browser` object; tests live outside `extension/` so they don't ship to AMO.

```
node --test tests/extension/              # or: npm test
```

Lint the JS with ESLint (the root `package.json` holds only dev tooling; run `npm install` once). `eslint.config.mjs`: `@eslint/js` recommended; `extension/` as plain browser scripts with the `browser` WebExtension global (cross-file names via `/* global */` and `/* exported */` comments), `tests/` as CommonJS for Node; `legacy/` is ignored. `npm run lint` also runs `addons-linter` on `extension/` (`npm run lint:amo`), the same checks AMO runs on an upload. It is used instead of `web-ext`, whose Android-debugging dependency carries a `node-forge` advisory with no fixed version. Keep both at 0 problems.

```
npm run lint                              # ESLint, then addons-linter
```

Type-check the host with pyrefly (configured in `pyproject.toml` `[tool.pyrefly]`: checks `host/`, excludes `legacy/`; keep it at 0 errors). The explicit `project-includes` matters: `host/src` is on the interpreter path as an editable install, so without it pyrefly skips the host package entirely.

```
uv run pyrefly check
```

Lint the Python with ruff (`dev` group; configured in `pyproject.toml` `[tool.ruff]`: line length 120, `legacy/` excluded, isort with `combine-as-imports` and `ytmp3_host`/`conftest` as first party, so the tests keep the blank line before them). Keep it at 0 problems. A broad `except Exception` belongs only at a boundary that must answer or keep running whatever fails; there it logs with `logger.exception` (the traceback goes to `mp3.log`) or carries a `# noqa: BLE001 - <reason>`. Every `subprocess.run` states `check=`.

```
uv run ruff check             # --fix applies the safe fixes; review the diff, some change behavior (e.g. an exception type)
```

Host tests use pytest (`dev` group) and live in `tests/host/` (`testpaths` in `pyproject.toml`). yt-dlp is replaced by `tests/host/fake_yt_dlp.py` (a script that takes the real yt-dlp arguments, including `--version`, and behaves according to `FAKE_YTDLP_*` env vars); `MP3.main()` is driven with framed bytes on a fake stdin/stdout. Autouse fixtures keep every test off GitHub (`no_github`) and point the updater's lock file and download folder into `tmp_path` (`update_paths`). `test_github.py` and `test_updater.py` test the real network code against a local HTTP server; there the fake `yt-dlp.exe` downloads are small Python scripts run as `python <file> --version`. `test_repair.py` tests `download_with_repair` with fake repairs (the fake's `needs_js` mode fails like YouTube wanting JavaScript, unless given `--js-runtimes`). Tests that need the real `ffmpeg.exe` (from `host/bin/` or `PATH`) are skipped without it. The `network` tests (a real download with the real binaries) are opt-in.

```
uv run pytest                 # all host tests except network
uv run pytest -m network      # real download with host/bin/yt-dlp.exe + ffmpeg.exe
```

`host/tests/smoke_native.py` is a manual script and not pytest-safe: it shells out to `yt-dlp.exe` at import time and spawns `dist/mp3/mp3.exe` (falling back to `python -m ytmp3_host.MP3`) with a hardcoded message.

## Architecture

### Message flow
0. The toolbar button (`browser_action`, `default_area: navbar`) toggles the sidebar (`sidebarAction.toggle()` in `background.js`, called directly in the click handler). It is there because with tabs on top Firefox shows no sidebar launcher, so users would not find the extension. Extensions can't hide or unpin it (only read `getUserSettings().isOnToolbar`), and detecting vertical tabs needs the `browserSettings` permission, so instead the sidebar asks `background.js` (`toolbar_tip`, `toolbarTipWanted`) whether to show `#toolbarTip`, which says how to unpin it: only when the button is pinned and the sidebar was opened without it (no click in the last 5 s, not a sidebar Firefox restored in its first 10 s), until dismissed (`storage.local.toolbarTipDismissed`).
1. `sidebar.js` / context menu → `browser.runtime.sendMessage({type: 'native_action', action, url, folder, filename, path})`.
2. `background.js` whitelists actions (`download`, `download_gui`, `select_folder`, `get_current_folder`, `show_in_folder`, `play`, `get_version`, `update_yt_dlp`, `update_host`) with a per-action timeout (`ACTION_TIMEOUTS_MS`), opens a **new** `connectNative('app_manifest')` port per request (`hostRequest`), and tags responses with the caller's `requestId`. After the final response it disconnects the port (which ends the host process), except for `download_gui`, whose process must stay alive to run the Tk window; that host exits by itself (`sys.exit(0)` in `MP3.download_gui`) when the window closes.
3. `MP3.main()` loops on `read_message()` and dispatches by `action` (unknown/missing action falls back to `download`).
4. Responses are dicts with `status` (`success`/`error`/`warning`), optional `message`/`filename`/`path`/`folder`, and `final`. `background.js` relays every response to the UI as `type: 'native_response'` and guarantees exactly one `final: true` message per request: the host's own, a synthesized error on timeout, or one on port disconnect (Firefox puts the reason on `port.error`; "No such native application" becomes a "not installed" message with `helpUrl` set to the installer download (`INSTALLER_URL`), which the sidebar renders as a link). Intermediate warnings must use `final: false`.
5. Context-menu downloads send the sidebar's saved folder (`storage.local.lastFolder`) when there is one. Desktop notifications are shown for `download` results only: always for context-menu downloads, and for sidebar downloads only if the sidebar is closed when the result arrives. Clicking a success notification sends `show_in_folder` for its `path`.
6. A successful download's `path` gives the sidebar's result "Show in folder" and "Play" buttons (`fileActions`), which send `show_in_folder`/`play` with that path; that result stays until the next one instead of hiding after 5 s. The host only opens an absolute path to an existing `.mp3` (`files.downloaded_mp3`): `play` opens it in its default app, which must never run a program.
7. `extension/youtube.js` holds the URL checks, loaded as a plain script by both the background and the sidebar: `isYouTubeUrl`, `isKnownSiteUrl` (a YouTube video or a track on `AUDIO_SITES`: SoundCloud, Bandcamp, Mixcloud; these get the context menu, whose `targetUrlPatterns` must cover them, and fill the sidebar's URL field) and `isWebUrl` (any http(s) URL, what the sidebar accepts when pasted: yt-dlp knows many sites). `extension/naming.js` (sidebar only) mirrors the host's `naming.filename_limit`: the filename field's `maxLength` follows the folder, and a name that no longer fits is refused before downloading (`test_versions.py` checks the constants match). `extension/formats.js` (sidebar only) lists the download formats (`FORMATS`: MP3, MP4 with `quality` and `codec`). The sidebar is one form: the MP3/MP4 switch shows the fields marked with that `data-format` and builds their selects from `FORMATS`; the format and choices are remembered (`storage.local.format`, `<format>Options`). MP3 requests carry no `format`, so every host understands them; any other format is sent (`format`, `quality`, `codec`, forwarded by `background.js`) only when the host's `get_version` answer lists it in `formats` (`hostSupports`), because an older host would ignore the field and download an MP3. The sidebar's `?` button opens `#help` ("How it works", a script-free `popover`), which explains the behavior users could be surprised by (naming, tags, folder, context menu, updates); keep it in step when that behavior changes.

### Versions, the handshake and repairs
- The host version is `ytmp3_host.__version__`; `pyproject.toml` and `MyAppVersion` in the installer repeat it. `tests/host/test_versions.py` checks they match, that `MIN_HOST_VERSION` in `background.js` is not above it, and that the installer's file name, version folder and self-check argument match what the updater, `config`, `MP3` and the extension's `INSTALLER_URL` expect. It also fails if `extension/manifest.json` asks for a permission 1.x did not have: Firefox holds back an update with a new required permission until the user approves it (use `optional_permissions` instead). Bump all three versions together.
- The sidebar sends `get_version` on every open. The host answers with facts only (`health.host_status`): `version`, `latest` (the newest host release tag), `outdated`, `self_update` (only an installed host can update itself), `yt_dlp` (`installed`, `version`, `latest`, `outdated`), `ffmpeg.installed`, `js_runtime` (`name`, `installed`). `None` means unknown (e.g. offline) and never triggers anything.
- `background.js` (`checkAndRepairHost`) then repairs what it can, each repair at most once per check. First comes `update_host`, when a newer host release exists and `self_update` is set; it then polls `get_version` every 5 s for up to 3 min until the new version answers. Then comes `update_yt_dlp`, when yt-dlp is missing, broken or outdated. Each step is relayed as an intermediate `info` response ("Updating yt-dlp..."). The state after the last repair goes through `assessHostStatus`, which turns it into one status: `success`, or a warning/error with `helpUrl`, the direct installer download (`INSTALLER_URL`), which fixes every host problem (a 1.x host that can't update itself, host older than `MIN_HOST_VERSION`, missing ffmpeg, missing/broken yt-dlp, outdated yt-dlp, or a host that closed without answering, i.e. a broken install), with the reasons of failed repairs appended. The sidebar shows it in the persistent `#hostNotice`. Concurrent checks (e.g. two windows) share one run; a sidebar that joins it gets the last progress message at once, then the later ones. For users who never open the sidebar, `checkHostInBackground` runs the same check silently, at most once a day (any check counts; its start time is `storage.local.lastHostCheck`): 1 min after browser startup and after a context-menu download. A missing JS runtime is reported but not shown: it is normal (yt-dlp works without one, faster), and the host installs Deno itself once a download needs it (`core.download_with_repair`).
- Compatibility is a minimum version, not an exact match: raise `MIN_HOST_VERSION` only when the extension starts to rely on a new host action or field.
- 1.x hosts don't know `get_version`: they treat it as a download without a URL and answer "Invalid YouTube URL" (`LEGACY_HOST_REPLY`), which marks them as outdated. Any other error without a `version` is relayed as it is.

### Backend modules (`host/src/ytmp3_host/`)
- `config.py` — installed, each host version lives in `<install dir>\versions\<version>\` (`BIN_DIR`: `mp3.exe`, `_internal\`, `ffmpeg.exe`, `mp3.ico`). `INSTALL_DIR` (`<install dir>`) holds what the host manages at runtime and all versions share: `yt-dlp\<tag>\` (`YT_DLP_DIR`: yt-dlp's onedir builds, `yt-dlp.exe` and `_internal\`, one per release), `yt-dlp.exe` (`YT_DLP_PATH`: the single-file build, only the fallback for a release whose onedir build failed, which `yt-dlp\onedir-failed` names; also the dev layout), `deno.exe` (`DENO_PATH`, only once a download needed it), `mp3.log`, `update.lock`. The yt-dlp the host runs is looked up on every use with `yt_dlp_path()`, since an update can change it, so never keep it in a module constant: the newest onedir build, unless `onedir-failed` names a release as new or newer and the single-file exe is there; without a build `YT_DLP_PATH`. `INSTALLED` is true only in that layout. A PyInstaller build run straight from `dist\mp3\` has everything next to `mp3.exe`. Unfrozen, `BIN_DIR` = `INSTALL_DIR` = `host/bin/` (place the binaries there manually) and the icon comes from `packaging/assets/`. `DEFAULT_FOLDER` is `YT-MP3-Downloads` in the real Documents folder (`documents_folder()`: `SHGetKnownFolderPath`, so one moved into OneDrive is found; `~/Documents` if that fails; hosts before 2.1.0 used `~/Documents`, and sidebar users keep that as their saved `lastFolder`). `setup_logging()` (called once from `MP3.py`'s `__main__`) writes one rotating `mp3.log` (1 MB, plus `mp3.log.1`): in `INSTALL_DIR` at ERROR when frozen, in the repo root at DEBUG (and to stderr, which Firefox shows in the Browser Console) unfrozen. The `YTMP3_LOG_LEVEL` env var overrides the level. The level applies to the `ytmp3_host` loggers; third-party libraries log WARNING and up.
- `native_messaging.py` — stdio framing (`read_message`/`send_message`, 4-byte native-endian length prefix) and `run_native()`, the headless download path: validates URL, resolves folder (a folder that doesn't exist is a final error naming it, `missing_folder_message`, never a silent fallback to the default; so is a relative path, which would resolve against the version folder; and a folder Windows won't let the host write to, tested with a probe file by `files.folder_is_writable` (opened with `O_TEMPORARY`, so Windows deletes it on close, even when the host is killed) before yt-dlp's "Permission denied" could look like a broken yt-dlp and start a repair), then calls `core.download_with_repair` (an empty filename means "name it after the video title"). `run_open_file()` handles `show_in_folder`/`play`.
- File opening (`files.show_in_folder`/`files.open_file`, used by the sidebar actions and the GUI): show uses the shell API `SHOpenFolderAndSelectItems`, because `explorer.exe /select,<path>` splits the path at commas. Play runs `explorer.exe "<path>"` through `processes.launch_detached` (its own module, so `play` doesn't load the updater and urllib): Explorer hands the file to the running shell, so the player doesn't belong to Firefox's job, which ends with the host.
- `naming.py` — `safe_filename` (strips invalid and control chars and bracket groups made only of noise words like "(Official Video)"; noise words elsewhere stay, e.g. "Live and Let Die"; prefixes Windows device names like `CON` with `_`), `requested_filename`, `filename_limit` (251 UTF-16 units, less in a deep folder: past 259 for the whole path Python can't see the file ffmpeg wrote; a too long typed name is an error before downloading, a too long title is shortened), artist/title from a filename, URL checks. No project imports.
- `metadata.py` — the video info yt-dlp prints (`INFO_FIELDS`, `parse_info`) and what comes from it: `title_filename`, `artist_for`, `extra_tags`.
- `files.py` — `ensure_default_folder`, `resolve_folder`, `folder_is_writable`, temp file cleanup, `downloaded_mp3`, `show_in_folder`, `open_file`.
- `ytdlp.py` — running yt-dlp: `build_download_command`, `run_yt_dlp` (the download with its watchdog), `find_thumbnail`, `kill_process_tree`.
- `core.py` — `describe_error` and `download_audio`, the single download pipeline used by both the headless and GUI paths:
  1. **One** `yt-dlp` call (`build_download_command`) downloads the audio, encodes MP3 V0, writes the raw thumbnail, and prints the video info (`INFO_FIELDS`, as JSON with `%(.{...})j`) after `INFO_MARKER` at the `before_dl` stage (`--no-simulate` keeps `--print` from making it a dry run). Output goes to a unique `_ytmp3_<hex>` temp stem; there is no separate `--get-title` call. When the title decides the name and that file already exists, the `on_title` callback raises `FileExistsError` before any audio is downloaded (checked again after the download).
  2. **One** `ffmpeg` pass (`embed_thumbnail`) copies the audio (no re-encode), center-crops the thumbnail to 1:1, encodes it as JPEG ID3v2.3 cover art, writes the tags, and writes the final `<filename>.mp3` directly. The artist is the text before the first spaced dash (` - `, ` – `, ` — `) in the filename (a dash inside a word, as in "Anti-Hero", does not separate); without one it comes from the video info: `artists` (YouTube Music and music sites; `info_artists` ignores Mixcloud's, which are a mix's tracklist), else the channel without " - Topic", else the uploader (`artist_for`). A file named after its title is `title_filename`: a title that doesn't start with `info_artists` before its spaced dash (or has none) gets them in front ("Forss - Flickermood"), never the channel (a vlog stays "Me at the zoo"). The title is the text after the dash (`title_from_filename`). `extra_tags` adds album, year (`release_year` only: an official video's upload year is often decades after the song), track number and the video URL as the comment, each only when the video has it. `embed_thumbnail` refuses an existing output itself: ffmpeg 7 exits 0 when `-n` declines to overwrite.
  3. Temp files are always removed in `finally` (`remove_temp_files` retries files Windows still locks after a kill). A host Firefox kills mid-download never reaches `finally`, so each download first deletes `_ytmp3_*` files older than `STALE_TEMP_AGE_S` (1 h) in its folder (`remove_stale_temp_files`). Raises `FileExistsError` (with `.filename`), `FileNotFoundError` (ffmpeg/yt-dlp missing), `subprocess.TimeoutExpired` (`DOWNLOAD_TIMEOUT_S` for yt-dlp, enforced by a watchdog; `EMBED_TIMEOUT_S` for ffmpeg) or `CalledProcessError`.
  - `download_with_repair` wraps `download_audio` for both paths. When yt-dlp fails or is missing (not ffmpeg, not a timeout, not a canceled GUI download), it runs `updater.update_yt_dlp()` and retries once, only if that installed a new exe. If the output shows a damaged install (`BROKEN_INSTALL_FAILURES`: `ImportError`, `ModuleNotFoundError`, `DLL load failed`, e.g. a virus scanner removed a DLL of the onedir build, which `--version` does not load), it runs `update_yt_dlp(damaged=True)`: a current onedir build is then handled like one that can't be installed (`onedir-failed`, the single-file exe for this release). It is never reinstalled, since the scanner would remove the file again and every download would download the build again; the next release tries onedir once more. If yt-dlp's output shows YouTube wanted a JavaScript challenge solved (`JS_CHALLENGE_FAILURES`) and there is no runtime, it also runs `updater.install_deno()`. Progress goes to `on_info` (the host sends it as `status: info`, `final: false`). `core` imports `health`/`updater` lazily: only this failure path loads them. `run_yt_dlp` leaves `[download]` progress lines out of the error output, so these warnings stay in it.
  - An installed `deno.exe` (`DENO_PATH`) is passed as `--js-runtimes deno:<path>` (yt-dlp only searches PATH). It costs ~5.5 s per download, so it is never installed up front. Without it, yt-dlp uses a Deno on PATH or YouTube clients that need no JavaScript.
  - Folder and filename helpers shared by both paths: `resolve_folder` (empty/default → created default folder, invalid → `None`), `requested_filename` (`""` = name after the title), `is_web_url` (the request check: http(s) with a host, which also keeps a URL from being read as a yt-dlp option). `is_youtube_url` only decides whether a failure may need Deno: other sites also print "Requested format is not available". `--playlist-items 1` keeps a playlist URL (SoundCloud set, Bandcamp album) to one file.
- `MP3.py` — entry point: the `ACTIONS` dispatch table and `main()` loop. It imports `gui`, `health`, `updater` and `selfcheck` with a PEP 810 `lazy from ... import` (module level only), so they load on first use in their handlers and headless `download`/`get_current_folder` requests never load customtkinter/Tk or urllib. The updater functions are bound as `install_yt_dlp`/`install_host_update`; tests patch them there. Started as `mp3.exe --self-check` (`SELF_CHECK_ARG`; Firefox passes other arguments), it runs `selfcheck.self_check()` instead of the request loop; started as `mp3.exe --install-yt-dlp` (`INSTALL_YT_DLP_ARG`), `install_yt_dlp_for_setup()`: `updater.update_yt_dlp()`, exit code 0, or 1 with the error in `mp3.log`. The installer runs both.
- `selfcheck.py` — what the installer runs on a new version before switching Firefox to it, all offline: imports every host module (`MODULES`; the lazy imports would only fail on first use, and a test checks the list is complete), starts a second process of the same version the way Firefox does (`host_command`) and expects exactly one framed answer to the `ping` action (`MP3.ping`: status and `version`, not used by the extension), checks HTTPS works (`ssl.create_default_context()`; without `ssl` urllib still imports but can't open https URLs, so the new version could never update itself), and runs the ffmpeg steps of a download on a generated 1 s tone and non-square image in a temp folder (libmp3lame V0 encode, then the real `core.embed_thumbnail`; the result must have the ID3v2.3 artist, title and cover frames). Exit code 0 or 1; problems go to `mp3.log` and stderr. yt-dlp is not checked (shared by all versions and repaired by the host), and nothing is downloaded, so no test URL can go stale.
- `health.py` — `host_status()` for `get_version`: runs `yt-dlp --version` (`read_version`: never raises, kills the tree on timeout, `None` for a missing, truncated, failing or hanging exe) while the GitHub lookup runs in a worker thread. `parse_version`/`is_outdated` compare dotted versions numerically (missing parts are 0). `find_js_runtime()` looks for `DENO_PATH`, then for `deno` on `PATH`. `deno_version_command` checks a Deno with `deno eval` (it prints the bare version, and proves it runs JavaScript).
- `github.py` — `latest_release_tag(repo)`: one HEAD request to `/<repo>/releases/latest`, reading the tag from the redirect's `Location` without following it (no REST API, so no 60/h rate limit). Returns `None` on any network problem. Used for yt-dlp's and the host's own releases (`HOST_REPO`).
- `updater.py` — `update_yt_dlp()` and `update_host()`. They raise `UpdateError` (with a message meant for the user) and never leave a broken tool:
  - Downloads are pinned to the tag `latest_release_tag` returned and checked against that release's SHA-256 list (yt-dlp's `SHA2-256SUMS`, the host's `SHA256SUMS`). `download()` also checks `Content-Length`, because a dropped connection can end the body without an error, and fsyncs the file. One update runs at a time: `update_lock()` is a Windows byte-range lock on `update.lock`, which Windows releases when the process dies, so there are no stale locks. A second host waits up to 60 s, then sees the update is done.
  - yt-dlp: installs the release's onedir build (`yt-dlp_win.zip`): downloaded and checked, unpacked to `yt-dlp\<tag>.download\` (member paths outside it or more than `MAX_UNPACKED_BYTES` are refused), test-run, then renamed to `yt-dlp\<tag>\`; a `<tag>` folder already there does not run and is replaced. Only when that build can't be installed here (`OnedirUnavailable`: no zip in the release's checksums, a bad zip, it does not run or can't be renamed; not a network problem or a checksum mismatch, which the single-file exe would have too) is the tag written to `yt-dlp\onedir-failed` and the single-file `yt-dlp.exe` used for that release (kept when current, else downloaded); the next release tries onedir first again. A current single-file exe without the marker (from a host before onedir) gets the onedir build, and is kept when a network problem stops that. Leftovers of a killed onedir install (`<tag>.download\`, `<tag>.download.zip`) are removed by the next update. The update itself never deletes older builds or the single-file exe: the installer runs it while Firefox still uses the previous host and its `yt-dlp.exe`. `remove_unused_yt_dlp()` does, on every `get_version` (whose answer comes from the version Firefox uses): only when the lookup finds a working onedir build, and never while an update holds the lock (it skips instead of waiting; the build's `--version` gets only `CLEANUP_VERSION_TIMEOUT_S`, 5 s, since `host_status` runs its own 20 s check after it within the extension's 30 s). It deletes `yt-dlp.exe` with its `.old`/`.download` leftovers, older builds and `onedir-failed`. While the lookup takes the single-file fallback instead, it deletes every onedir build (the lookup can't take them, e.g. a damaged one) and keeps the exe and the marker. An older build is first renamed to `<tag>.download\`: one another host still runs can't be renamed, so it stays whole (rmtree would delete only the files Windows allows and break that download), and a later call removes it. The single-file exe downloads to `yt-dlp.download.exe`, test-runs `--version` on it, then swaps it in with two renames (current -> `yt-dlp.old.exe`, new -> `yt-dlp.exe`; a running exe can be renamed, not overwritten) and deletes the old copy. `recover_yt_dlp()` runs first. It restores the newest `.old` copy when `yt-dlp.exe` is missing (killed between the renames; works offline) and deletes leftovers. An `.old` copy still running in another host can't be deleted and stays until a later update; meanwhile a swap uses a unique `.old-<hex>` name. Offline with a working yt-dlp is not an error.
  - Deno (`install_deno()`, only from `core.download_with_repair`): the latest `denoland/deno` release's `deno-x86_64-pc-windows-msvc.zip`, checked against its `.sha256sum` (PowerShell `Get-FileHash` list format, so the hash is found by regex), unpacked to `deno.download.exe`, test-run, renamed to `deno.exe`. The zip is deleted right after unpacking. The leftovers of a killed install (`deno.download.zip`/`.exe`) are removed by the next `install_deno` or `update_yt_dlp`, under the update lock. A working `deno.exe` is kept. Never updated afterwards (like ffmpeg; see PLAN).
  - Host: downloads `YT-MP3-Downloader-Setup.exe` to `%TEMP%\ytmp3-update\<tag>\` (a verified copy is reused) and starts it with `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP-` via `processes.launch_detached`. That uses `DETACHED_PROCESS` + `CREATE_BREAKAWAY_FROM_JOB`, so Firefox's job doesn't kill it along with the host; without breakaway permission it retries inside the job. It starts the process in the temp folder: inheriting the host's working directory (its version folder) would keep the installer from removing that folder. The installer is not started again for 10 min (`INSTALL_GRACE_S`). After that the host is still outdated, so the install failed: the same installer (the `started` marker holds its SHA-256) is not retried for 24 h (`INSTALL_RETRY_S`; `update_host` fails at once instead, so the sidebar shows the installer link without 3 min of "Updating..."), while a release re-published under the same tag with a new installer is started right away. Refuses in a source checkout (`config.INSTALLED`). `remove_installed_downloads()` runs on every `get_version` (so first by the new version, when the extension polls for it). It deletes the download folders of this release and older ones, and the folder itself once empty; a newer release's download is kept. Files the still-finishing installer holds open are retried on the next call.
- `gui.py` — the customtkinter window (`DownloaderApp(ctk.CTk)`) plus `open_gui`/`select_folder`. Downloads go through `core.download_with_repair` (`on_progress`/`on_start` callbacks for the progress bar and cancel, `on_info` for repair messages, `is_cancelled` so a canceled download is not repaired). After a save, `show_saved` shows "Show in folder" and "Play" below the status. Tk is touched only on the main thread: `start_download` reads the fields and passes them to the worker thread, which updates widgets only via `after(0, ...)`.

### Constraints to keep in mind
- **stdout is the native-messaging channel.** Never `print()` in backend code that runs under the host; log through a module-level `logger = logging.getLogger(__name__)`, never the root `logging.*` functions (`MP3.py` names its logger `ytmp3_host.MP3` explicitly, because its `__name__` is `__main__`). Child processes must get `stdin=subprocess.DEVNULL` (and ffmpeg `-nostdin`), or they can consume bytes from the native-messaging stdin.
- `Popen.kill()` stops only yt-dlp itself, while its ffmpeg child (and with the single-file `yt-dlp.exe`, a PyInstaller onefile build, the real yt-dlp behind its bootloader) keeps running and holds the pipe open. Stop it with `ytdlp.kill_process_tree` (`taskkill /T`).
- Keep the host startup path light: no heavy imports (customtkinter, Pillow) at module level in anything the headless `download` path imports. Pillow is a dev-only dependency (icon helper in the smoke test) and is excluded from the build.
- The identifiers `app_manifest` (native host name) and `yt.downloader@converter.org` (extension ID) must match across `background.js`, `extension/manifest.json`, `packaging/app_manifest.dev.json`, and the `#define`s in `packaging/installer/mp3_installer.iss`. Changing either breaks existing v1 installs and AMO updates.
- The installer has no `AppId`, so `AppName` is the AppId; it must stay what 1.x used, or an update installs as a second app. It writes the native-messaging manifest as pure ASCII (`JsonEscape` turns non-ASCII into `\uXXXX`: `SaveStringToFile` writes the ANSI code page, Firefox reads UTF-8, so an accented user name would break it) to `%APPDATA%\Mozilla\NativeMessagingHosts\app_manifest.json` and registers it under `HKCU\Software\Mozilla\NativeMessagingHosts\app_manifest`. yt-dlp is not bundled: after the self-check the installer runs the new version's `mp3.exe --install-yt-dlp` (hidden), so the host's own `update_yt_dlp()` installs it into `{app}\yt-dlp\` (`YtDlpDir`, `test_versions.py` checks it and the argument); a working, current one is kept. Exit code 1 does not stop the installation; the host's repair installs yt-dlp on the next sidebar check. `[UninstallDelete]` lists everything the host creates at runtime (the `yt-dlp\` folder, `yt-dlp*.exe`, `deno.exe`, ...), and the `[Files]` excludes leave it out of `dist\mp3\`. x64 (and ARM64, emulated) only: `ArchitecturesAllowed=x64compatible`.
- The installer must never leave a half-installed or broken host, because a host that can't start can't repair itself. Each version goes into its own `versions\<version>\` folder and must pass `mp3.exe --self-check` there; if it fails, its folder is removed (unless it is a reinstall of the running version), nothing is switched and Setup exits with code 1. Only after all its files (and yt-dlp) are in place is the manifest switched to it, atomically: written to `.tmp`, then `MoveFileExW` with replace. Then the other version folders are removed (except one whose `mp3.exe` is still running), along with the files of a 1.x install in `{app}`. A kill or power loss before the switch leaves Firefox on the old, complete version. `CloseApplications=no`, because a new version never touches files a running host uses.
- URL validation differs between halves: the extension parses the URL (`youtube.js`; known sites strictly for the context menu and autofill, any http(s) URL when pasted), while the Python side (`naming.is_web_url`) only requires an http(s) URL with a host; yt-dlp reports unsupported sites.
- Downloads can legitimately run for minutes (host: 900s `DOWNLOAD_TIMEOUT_S` for the whole yt-dlp call, plus a repair and one retry in `download_with_repair`, about 50 min at worst); keep `ACTION_TIMEOUTS_MS.download` (51 min, `test_versions.py` checks it) above that. The same goes for `update_yt_dlp` (~595 s worst case: a onedir build that fails its test-run, then the single-file exe; 11 min, also checked) and `update_host` (~485 s, 9 min); the sums are in the comment above `ACTION_TIMEOUTS_MS`.
